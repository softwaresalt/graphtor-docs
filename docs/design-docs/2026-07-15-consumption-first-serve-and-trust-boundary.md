## Context

graphtor-docs plays two distinct roles that share one binary:

* **Authoring / dev workspace** — a workspace with a real `sources.yaml` that
  points at docline output. This workspace ingests documents, generates a
  database, and re-syncs incrementally as sources change.
* **Consumption workspace** — a workspace that only wants to serve
  already-generated documentation context to an AI agent over MCP. No
  ingestion happens here; a `.db` file (built elsewhere) is simply dropped
  into place and served read-only.

Before this pivot, `serve` treated every workspace as a potential authoring
workspace: it resolved databases only from `sources.yaml`/`--db-path`, opened
every database read-write, and unconditionally spawned a background sync task
whenever any source was configured. A consumption workspace with no
`sources.yaml` had no way to serve a dropped database at all, and any
workspace with resolvable sources risked mutating a database an agent expected
to be a stable, read-only reference.

This document describes the resulting **consumption-first serve** design:
zero-config auto-discovery is the default, read-only is the fail-safe posture,
and write/sync behavior is enabled only when the workspace demonstrably has
real, resolvable generation sources.

## The docline → graphtor-docs → agent pipeline

At a high level, documentation flows through three stages before an AI agent
ever sees it:

```text
docline (external tool)          graphtor-docs                    AI agent
─────────────────────────   ─────────────────────────────    ─────────────────
Normalizes source docs      Acquire → Validate → Parse →     MCP tools over
into contract-conformant    Embed → Load into a CozoDB/       STDIO: search,
Markdown (frontmatter,      SQLite-backed .db file           search_semantic,
chunking, hashing) — see                                     research_topic,
graphtor-docs-ingestion-    (ingestion side; see              traverse_doc_links,
contract.md                 docs/pipeline.md for the          list_sources,
                             detailed 5-stage pipeline)        get_chunk, ...
                                     │
                                     ▼
                             `graphtor-docs serve`
                             auto-discovers and serves
                             the resulting .db file(s)
```

The **ingestion** half of this pipeline (Acquire → Validate → Parse → Embed →
Load) is documented in detail in [Pipeline Reference](../pipeline.md) and the
docline contract surface in
[docline → graphtor-docs ingestion contract](graphtor-docs-ingestion-contract.md).
This document covers the **serve** half: how a resulting `.db` file is
discovered, classified, and exposed to an agent — including the important case
where a workspace only ever runs `serve`, never `sync`.

## `.graphtor/` workspace layout

Every graphtor-docs workspace is rooted at a `.graphtor/` directory relative
to the current working directory:

| Path | Purpose |
|---|---|
| `.graphtor/config/sources.yaml` (or `*.sources.yaml`) | Source registry — optional in a consumption workspace |
| `.graphtor/*.db` | Database file(s) — either generated by `sync` or dropped in directly |
| `.graphtor/bin/` | Scaffolded binary location for a full (ingestion-capable) install |
| `.graphtor/data/` | Reserved for future ingestion-scoped data |
| `.graphtor/cache/` | Embedding model cache and other cached artifacts |
| `.graphtor/logs/` | Log output location |

A consumption workspace needs only `.graphtor/` itself plus a dropped `.db`
file — none of the other subdirectories are required for `serve` to work.
`bin/`, `data/`, `cache/`, `config/`, and `logs/` are scaffolded by a full
`install`; Phase 2 of this same body of work makes that scaffold opt-in (see
[Configuration Guide](../configuration.md) and the CLI reference's `install`
section for the current default footprint).

## Serve auto-discovery and content-derived posture

`serve` resolves the set of databases to open as the union of:

1. **Configured/explicit candidates** — targets resolved from
   `sources.yaml` (including a generation target that does not exist yet), or
   an explicit `--db-path` value.
2. **Explicit workspace-contained `type: database` entries** — an optional,
   additive `sources.yaml` entry that names a specific database to serve
   read-only (see [Configuration Guide](../configuration.md#source-type-database-type-database)).
3. **Auto-discovered `.db` files** — every file directly inside `.graphtor/`
   whose extension is exactly `.db`. The scan is intentionally **non-recursive**
   (subdirectories such as `models/` are structurally excluded), skips
   symlinks and reparse points, and never descends into or serves anything
   outside `.graphtor/` itself.

Every path in this union is then classified into one of two postures,
purely from **content**, never from a hardcoded path, environment variable,
or manual flag:

| Posture | When it applies | Behavior |
|---|---|---|
| `ReadOnly` | The fail-safe default: no `sources.yaml`, an empty or stale registry, or a database with no source targeting it (including any auto-discovered dropped file) | Opened via the engine-enforced read-only primitive (below); never background-synced |
| `Generation` | A `local` source whose configured `path` exists on disk AND contains at least one file matching that source's `formats`/`include`/`exclude` filters, resolved to exactly this database's target | Opened read-write; the workspace's normal incremental background sync runs |

Only sources that actually resolve to `Generation` are ever handed to the
background sync task — a stale or read-only-classified source group can never
be re-split into a background write, even if `sources.yaml` still lists it.

## The dev/authoring-workspace generation exception

The graphtor-docs repository's own development workspace is the canonical
example of the `Generation` case: it has a real `sources.yaml` pointing at
docline-produced Markdown under an existing, non-empty directory, so its
target database resolves to `Generation` and retains full generate-and-serve
behavior with no regression. This is intentional — the content-derived rule
exists precisely so that a workspace with genuine, resolvable sources keeps
working exactly as it always has, while every other workspace defaults to the
safer read-only posture.

A workspace can also be **mixed**: one database resolves to `Generation`
because a real source targets it, while an unrelated, co-resident dropped
`.db` file in the same `.graphtor/` directory stays `ReadOnly` because no
source targets it. Posture is resolved **per database**, not per workspace.

## Read-only serve hardening

A database classified `ReadOnly` is opened through an **engine-enforced**
read-only primitive, not merely an application-level guard:

* The database file (and any existing WAL/SHM sidecars) is marked
  filesystem-readonly before the underlying storage engine opens it, so every
  connection — including later pool refills — is genuinely denied write access
  at the OS/filesystem level, not just gated by application code.
* This was proven empirically: a direct, engine-level mutation attempt that
  bypasses the application's own read/write guard still fails, and a full
  read-only query cycle leaves the database file byte-identical afterward.
* The v4 schema pre-sync gate applies identically whether a database was
  auto-discovered or explicitly configured: a pre-v4 database is refused with
  a `run graphtor-docs sync to rebuild the index` message rather than served
  with stale data.
* The query language `serve` exposes to an agent has no raw-SQL escape hatch —
  there is no way to reach the underlying storage engine with an `ATTACH
  DATABASE` or `load_extension()` call through any tool `serve` exposes.

Together these guarantees mean a consumption workspace can never have its
served database mutated by `serve` itself, regardless of what an agent asks
for.

## `--read-only` escape hatch

`serve --read-only` forces **every** database in the served set to `ReadOnly`
posture, regardless of what `sources.yaml` would otherwise resolve — including
a database with a real, resolvable source pointing at it. This is useful when
an operator wants to inspect or serve a normally-generative workspace without
any possibility of a background sync running.

There is no corresponding "force read-write" flag: read-only is already the
fail-safe default, so forcing the safer posture is the only escape hatch this
phase provides.

## Optional explicit read-only database entries (`type: database`)

`sources.yaml` supports an additive `type: database` entry for naming a
specific database to serve read-only, independent of auto-discovery. See
[Configuration Guide](../configuration.md#source-type-database-type-database)
for the full field reference. Like auto-discovered entries, an explicit
`type: database` path must stay within the workspace root — an out-of-root
path (`..`, a symlink, or a Windows junction/reparse point escape) is rejected
rather than served, and external-path support is out of scope for this phase.

## Operator trust boundary

Auto-discovery means **any** `.db` file dropped into `.graphtor/` is served to
an AI agent as authoritative context — graphtor-docs does not, and cannot,
validate where that file came from or what it contains beyond the schema
version gate. This has a direct consequence for operators:

> **Only drop `.db` files into `.graphtor/` from sources you trust.** A
> discovered database is served as-is; its content is treated as legitimate
> documentation context for the agent, with no provenance check, signature
> verification, or content review at discovery time.

This trust boundary is a deliberate trade-off: it is what makes zero-config
consumption workspaces possible (an operator can simply copy a `.db` file into
place with no configuration step), but it means the workspace operator — not
graphtor-docs — is responsible for only placing databases built from trusted
ingestion runs into a served workspace.
