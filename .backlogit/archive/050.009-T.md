Prove an ENGINE/FILESYSTEM-level read-only open primitive for the Cozo SQLite backend BEFORE any other Phase-1 work begins. This is the Phase-1 ROOT GATE: P1-T1 (050.002-T) depends on it, so the entire Phase-1 chain — and shipment 045-S — is gated on this proof. CozoDB's public SQLite backend opens a WRITE-capable DbInstance and ignores the options string (src/db/store.rs:366-373,383-390), and the current open_sqlite_readonly enforces read-only ONLY at the DataStore mutate-guard boundary (src/db/store.rs:105-134), NOT at the engine/filesystem level. This task implements and PROVES a real engine-level read-only open that cannot create or mutate the db or its WAL/SHM/journal/lock sidecars (SQLite immutable=1/mode=ro URI or an equivalent SQLITE_OPEN_READONLY connection), verified by an automated before/after no-write proof. Scope is the primitive plus its proof ONLY (<= 2 files: src/db/store.rs plus a fixture builder if required); v4 gate parity and ATTACH/extension/single-file serve hardening move to P1-T4 (050.003-T), which consumes this primitive. If the engine-level no-write guarantee cannot be PROVEN, the FEASIBILITY STOP CONDITION fires (see Implementation Notes): this task AND shipment 045-S are BLOCKED and Dark Mode HALTS before Phase 2 / minimal install — never a write-capable handle, never an INV-1 claim on the DataStore mutate-guard alone, never a silent degrade. Sequence FIRST in Phase 1. Test-first.

<!-- BEGIN:acceptance-criteria -->
Three verification scenarios (the feasibility proof; all substantive checks retained):

(a) Engine/filesystem no-write proof — capture the target `.db` metadata (size, mtime, content hash) and assert NO creation or mutation of the db or its `-wal`/`-shm`/`-journal`/lock sidecars before AND after a full read cycle (query + search + semantic) against the read-only store (hash and mtime unchanged; no sidecar created).

(b) Engine-boundary write rejection — an attempted write/mutation against the read-only store is rejected at the ENGINE boundary itself (immutable/`mode=ro` or `SQLITE_OPEN_READONLY`), not merely at the DataStore mutate-guard.

(c) Feasibility gate — the read-only open is proven to use a backend/open mode that cannot write (immutable=1/`mode=ro` URI or equivalent `SQLITE_OPEN_READONLY`). If engine-level read-only cannot be PROVEN for the Cozo SQLite backend, the feasibility STOP CONDITION applies — this task (050.009-T / P1-T0) AND shipment 045-S are BLOCKED; never a silent degrade or an INV-1 claim on the mutate-guard alone.

Implementation footprint: <= 2 files (src/db/store.rs plus an optional test fixture builder) and ONE atomic milestone — a proven engine-enforced read-only open primitive with a passing before/after no-write proof.
<!-- END:acceptance-criteria -->
