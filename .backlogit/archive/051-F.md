        Consumption-first `install`: default to a minimal serve-only footprint; make ingestion scaffolding opt-in; document ingestion setup separately.

        Motivation / product framing: graphtor in a consumer (agent) workspace is a READ-ONLY context server, not a sync engine (see stash 79B5A7BC). Installing into a new workspace should therefore NOT scaffold ingestion machinery by default. Only the graphtor dev/authoring workspace (with real docline sources) needs the generation/sync scaffold.

        Current behaviour (verified):
        - `install()` (src/workspace/install.rs:34-45) creates ALL of `.graphtor/{bin,data,cache,config,logs}` from GRAPHTOR_SUBDIRS (src/workspace/paths.rs: GRAPHTOR_SUBDIRS = ["bin","data","cache","config","logs"]) and copies the running binary into `.graphtor/bin/`.
        - cmd_install (src/main.rs:3002) then calls init_sources_yaml (src/main.rs:3018 -> src/workspace/init.rs) writing a template `.graphtor/config/sources.yaml`, and generate_mcp_config (src/main.rs:3028) writing/merging `.mcp.json`.
        - Post-install message (src/main.rs:3080) tells the user to "edit .graphtor/config/sources.yaml to add documentation sources" — ingestion-oriented.
        - Note: bin/data/cache/config/logs all support ingestion/generation; serve only needs the .graphtor root (to hold dropped .db files) + a resolvable binary + .mcp.json.

        Desired behaviour:
        - `install` default (consumption-first): create only what serve needs — the `.graphtor/` root (where operators drop .db files) and a minimal `.mcp.json` (command graphtor-docs, args ["serve"]). Do NOT write sources.yaml. Do NOT create config/bin/cache/data/logs. Post-install message should explain "drop a .db into .graphtor/ to serve it read-only" and link to the ingestion-setup docs.
        - Ingestion/generation scaffold becomes OPT-IN: e.g. `graphtor-docs install --with-ingestion` (or the existing `graphtor-docs init` / a dedicated setup command) creates config + sources.yaml + data/cache/logs (+ bin/binary copy if used) for authoring/build workspaces. The graphtor dev workspace uses this path.
        - Binary resolution for serve: consumption workspaces typically use a globally-installed `graphtor-docs` on PATH (so no `.graphtor/bin/` copy needed); .mcp.json should reference the PATH command by default, and only use `.graphtor/bin/graphtor-docs` when the ingestion/bin scaffold was created. Decide the resolution/precedence.

        Documentation: add a SEPARATE docs section covering how to set up ingestion/sync of docline-produced source content (generation-side): creating the ingestion scaffold, authoring sources.yaml, running sync, and how the generated .db is then consumed read-only in agent workspaces. Keep the default install docs focused on the consumption/serve path.

        Cross-cutting / considerations: install/uninstall/upgrade parity (uninstall must clean up whichever footprint was created; upgrade of a consumption install has no bin copy to replace); doctor expectations (doctor currently assumes config/data etc. — must tolerate the minimal consumption layout); idempotency; backward compat for existing full installs; the graphtor dev workspace must retain the full generation scaffold; .gitignore/.graphtor artifact expectations. Depends on / pairs with 79B5A7BC (serve read-only auto-discovery of .graphtor/*.db) — a minimal consumption install only makes sense once serve auto-discovers dropped dbs; sequence 79B5A7BC first or ship together.

        Acceptance (high level): `graphtor-docs install` in a fresh consumer workspace creates only `.graphtor/` + a minimal serve `.mcp.json`, no sources.yaml and no config/bin/cache/data/logs; dropping a .db into `.graphtor/` makes it queryable read-only (via 79B5A7BC); an explicit opt-in flag/command scaffolds the ingestion/generation layout; uninstall cleans up correctly; docs have a distinct ingestion/sync setup section; the graphtor dev workspace keeps full generation capability.
