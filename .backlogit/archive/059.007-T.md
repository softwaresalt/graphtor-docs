Before dependencies are added to the product manifest, use an isolated throwaway harness to discover a cap-std candidate and prove with safe APIs under Rust 1.75 that the workspace-root authority can be bootstrapped no-follow/no-reparse, converted into the selected capability File/Dir boundary, and used for a beneath-root refusal matrix. U7 PASS. Committed evidence (companion to the same review request on 059.008-T -- persisted here, not only in the gitignored .backlogit/logs/ JSONL history):

Isolated throwaway harness (git-ignored under target/feasibility/u7-cap-std-harness/, deleted after evidence capture per this task's own 'isolated throwaway harness' framing) proved all 3 scenarios under both stable rustc and pinned rustc 1.75.0:
Scenario 1: newest compiling candidate = cap-std 4.0.3 (cap-primitives 4.0.3; transitive rustix 1.1.4, io-lifetimes 2.0.4/3.0.1, io-extras 0.19.0, windows-sys 0.59.0/0.60.2/0.61.2). cap-std 3.4.6 also compiles under 1.75; 4.0.3 is the proven candidate since it is newest.
Scenario 2: Dir::open_ambient_dir(root, ambient_authority()) bootstraps the workspace-root handle (trusted-parent threat model: the immediate parent of root is trusted not to swap root itself between process start and this call -- the same ambient-authority boundary every std::fs ambient call already carries). File boundary DECIDED: cap_std::fs::File::into_std() -> std::fs::File.
Scenario 3: table-driven refusal matrix all refused as required: (a) absolute path, (b) '..' escape, (c) intermediate-directory symlink swap via Dir::open_with beneath root_dir, (d) in-bounds leaf symlink -- the Windows leaf case additionally required an EXPLICIT post-open reparse-attribute check (open succeeds on a reparse point; FILE_ATTRIBUTE_REPARSE_POINT must be checked via MetadataExt::file_attributes() after open), confirming U2's should_refuse_reparse design is necessary, not optional.
No in-crate unsafe; #![forbid(unsafe_code)] compatible. Evidence gathered on a Windows dev host with rustc 1.75.0 + stable. Full narrative also recorded in docs/memory/2026-08-29/ship-051-s-feasibility-blocked-memory.md and PR #111.
