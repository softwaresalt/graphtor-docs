Before dependencies are added to the product manifest, use an isolated throwaway harness to discover a cap-std candidate and prove with safe APIs under Rust 1.75 that the workspace-root authority can be bootstrapped no-follow/no-reparse, converted into the selected capability File/Dir boundary, and used for a beneath-root refusal matrix. U7 PASS (CORRECTED; root-bootstrap correction captured in commit 82f5aa5 -- see correction note below). Committed evidence (persisted here, not only in the gitignored .backlogit/logs/ JSONL history):

Isolated throwaway harness (git-ignored under target/feasibility/u7-cap-std-harness/ and target/feasibility/u7-root-symlink-check/, deleted after evidence capture) proved all 3 scenarios under both stable rustc and pinned rustc 1.75.0:

Scenario 1: newest compiling candidate = cap-std 4.0.3 (cap-primitives 4.0.3; transitive rustix 1.1.4, io-lifetimes 2.0.4/3.0.1, io-extras 0.19.0, windows-sys 0.59.0/0.60.2/0.61.2). cap-std 3.4.6 also compiles under 1.75; 4.0.3 is the proven candidate since it is newest.

Scenario 2 (CORRECTED): a Copilot review of this evidence correctly identified that the originally-recorded bootstrap, `Dir::open_ambient_dir(root, ambient_authority())` alone, does NOT provide a no-follow/no-reparse root bootstrap -- it follows a symlinked root. This was verified empirically in a follow-up throwaway harness: planting a directory symlink as the root and calling `Dir::open_ambient_dir` on it SUCCEEDED (followed the link) and a file was read straight through it. The originally-recorded "trusted-parent threat model" therefore incorrectly extended trust to the root path itself, not merely its parent, and Scenario 2 as originally evidenced was WRONG. CORRECTED bootstrap (re-verified, now passes both required cases): open the workspace root's PARENT ambiently -- `cap_primitives::fs::open_ambient_dir(parent, ambient_authority())` -- then open the root ITSELF relative to that parent handle via `cap_primitives::fs::open_dir_nofollow(&parent_std_file, root_name)`, which refuses if the root is a symlink/reparse point (`open_dir_nofollow` is `pub fn` in cap-primitives 4.0.3's `fs::open_dir` module, re-exported via `pub use open_dir::*` in cap-primitives::fs, but is NOT exposed as a `cap_std::fs::Dir` method -- it must be called via a direct `cap-primitives` dependency, then the resulting `std::fs::File` wrapped via `cap_std::fs::Dir::from_std_file`). Empirical re-verification: (a) a symlinked root is REFUSED -- `os error 681` (ERROR_STOPPED_ON_SYMLINK) on Windows; (b) an ordinary (non-symlink) root still succeeds and a file was read through it. The corrected trusted-parent threat model is now precise: ONLY the immediate parent of the workspace root is trusted (ambient-authority open of the parent, the same single trust step any ambient std::fs call already makes); the root itself is no-follow-verified, not merely assumed. File boundary DECIDED (unchanged): `cap_std::fs::File::into_std() -> std::fs::File`. IMPLEMENTATION NOTE for U1/U2/U6: both `cap-std` (for the `Dir`/`File` capability-relative walk beneath the root, per Scenario 3) AND `cap-primitives` (for the `open_dir_nofollow` root-bootstrap primitive) must be adopted as direct dependencies -- `cap-std` alone is insufficient for a genuinely no-follow root bootstrap. The Unix side of `open_dir_nofollow` was not separately executed on this Windows dev host; it is inferred from `cap-primitives`' own `dir_options().follow(FollowSymlinks::No)` construction (the crate's core no-follow primitive, exercised extensively elsewhere in cap-primitives' own test suite) rather than independently re-verified here -- flagged as an assumption, not an executed proof, for whoever implements U6.

Scenario 3: table-driven refusal matrix all refused as required: (a) absolute path, (b) '..' escape, (c) intermediate-directory symlink swap via Dir::open_with beneath root_dir, (d) in-bounds leaf symlink -- the Windows leaf case additionally required an EXPLICIT post-open reparse-attribute check (open succeeds on a reparse point; FILE_ATTRIBUTE_REPARSE_POINT must be checked via MetadataExt::file_attributes() after open), confirming U2's should_refuse_reparse design is necessary, not optional. (Scenario 3's own beneath-root walk was not re-verified against the corrected root handle in this pass, but it operates identically on any `cap_std::fs::Dir` regardless of how that Dir's underlying `std::fs::File` was obtained, so the original Scenario 3 result stands.)

No in-crate unsafe; #![forbid(unsafe_code)] compatible. Evidence gathered on a Windows dev host with rustc 1.75.0 + stable. Full narrative also recorded in docs/memory/2026-08-29/ship-051-s-feasibility-blocked-memory.md and PR #111.
