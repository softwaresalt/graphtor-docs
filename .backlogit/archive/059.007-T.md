Before dependencies are added to the product manifest, use an isolated throwaway harness to discover a cap-std candidate and prove with safe APIs under Rust 1.75 that the workspace-root authority can be bootstrapped no-follow/no-reparse, converted into the selected capability File/Dir boundary, and used for a beneath-root refusal matrix. PASS records exact versions/APIs. BLOCKED names the failed obligation and keeps U8/U1/U6/U9/U2-U5/U10/U11 gated; no dependency or path-based fallback is added.

Scenario 2 (CORRECTED, now dual-platform AND dual-toolchain executed): a Copilot review of this evidence correctly identified that the originally-recorded bootstrap, `Dir::open_ambient_dir(root, ambient_authority())` alone, does NOT provide a no-follow/no-reparse root bootstrap -- it follows a symlinked root. Verified empirically: planting a directory symlink as the root and calling `Dir::open_ambient_dir` on it SUCCEEDED (followed the link) and a file was read straight through it. The originally-recorded "trusted-parent threat model" therefore incorrectly extended trust to the root path itself, not merely its parent, and Scenario 2 as originally evidenced was WRONG. CORRECTED bootstrap (re-verified, now passes both required cases on BOTH platforms under BOTH toolchains): open the workspace root's PARENT ambiently -- `cap_primitives::fs::open_ambient_dir(parent, ambient_authority())` -- then open the root ITSELF relative to that parent handle via `cap_primitives::fs::open_dir_nofollow(&parent_std_file, root_name)`, which refuses if the root is a symlink/reparse point (`open_dir_nofollow` is `pub fn` in cap-primitives 4.0.3's `fs::open_dir` module, re-exported via `pub use open_dir::*` in cap-primitives::fs, but is NOT exposed as a `cap_std::fs::Dir` method -- it must be called via a direct `cap-primitives` dependency, then the resulting `std::fs::File` wrapped via `cap_std::fs::Dir::from_std_file`).

WINDOWS re-verification (stable AND +1.75.0): (a) a symlinked root is REFUSED -- `os error 681` (ERROR_STOPPED_ON_SYMLINK); (b) an ordinary (non-symlink) root still succeeds and a file was read through it.

LINUX re-verification (stable AND +1.75.0, real execution on Ubuntu 26.04 via WSL2, not inferred). Persisted command/output under the required pinned toolchain:
    $ cargo +1.75.0 run --quiet
    CASE 1 (symlinked root) OK: bootstrap_root_nofollow refused it: Not a directory (os error 20) (kind=NotADirectory, raw_os_error=Some(20))
    CASE 2 (normal root) OK: bootstrap succeeded and file read through it

  (a) a symlinked root is REFUSED -- `os error 20` (ENOTDIR, "Not a directory") via both the full bootstrap helper and a raw direct call to open_dir_nofollow; (b) an ordinary (non-symlink) root still succeeds and a file was read through it. ENOTDIR (rather than ELOOP) is the observed refusal signal for this cap-primitives/kernel combination when a symlink is opened with the directory + no-follow options combined; the open FAILS and the symlink is never followed either way, which is what this gate requires. The stable-toolchain run (rustc 1.98) produced identical results before the +1.75.0 run above was captured as the toolchain-of-record for this gate.

The corrected trusted-parent threat model is now precise: ONLY the immediate parent of the workspace root is trusted (ambient-authority open of the parent, the same single trust step any ambient std::fs call already makes); the root itself is no-follow-verified on BOTH platforms, under BOTH the repository's actual toolchain and the pinned MSRV toolchain, by actual execution -- not assumed, not inferred, not partially proven. File boundary DECIDED (unchanged): `cap_std::fs::File::into_std() -> std::fs::File`. IMPLEMENTATION NOTE for U1/U2/U6: both `cap-std` (for the `Dir`/`File` capability-relative walk beneath the root, per Scenario 3) AND `cap-primitives` (for the `open_dir_nofollow` root-bootstrap primitive) must be adopted as direct dependencies -- `cap-std` alone is insufficient for a genuinely no-follow root bootstrap.

Scenario 3: table-driven refusal matrix all refused as required (Windows execution, stable + 1.75.0): (a) absolute path, (b) '..' escape, (c) intermediate-directory symlink swap via Dir::open_with beneath root_dir, (d) in-bounds leaf symlink -- the Windows leaf case additionally required an EXPLICIT post-open reparse-attribute check (open succeeds on a reparse point; FILE_ATTRIBUTE_REPARSE_POINT must be checked via MetadataExt::file_attributes() after open), confirming U2's should_refuse_reparse design is necessary, not optional. (Scenario 3's own beneath-root walk was not separately re-executed on Linux, nor re-verified against the corrected root handle from Scenario 2; it operates identically on any cap_std::fs::Dir regardless of how that Dir's underlying std::fs::File was obtained, so the original Windows-executed Scenario 3 result stands as the recorded evidence -- this narrower scope is noted explicitly rather than implied as cross-platform-executed.)
