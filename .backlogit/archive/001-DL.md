# PDFium dual backend for large PDF ingestion

## Problem Frame

<!-- BEGIN:problem-frame -->
The pdf-extract optimizations shipped in 023-F (PageTextAccumulator, histogram sampling, logging suppression) are insufficient for PDFs ≥100 MB. The bottleneck is architectural: lopdf::load_mem() eagerly parses all xref entries serially, which takes >20 minutes for a 104 MB PDF. No amount of optimization to our code can fix this — the bottleneck is inside lopdf before our code runs. The prior spike rejected pdfium-render because it "requires Pdfium runtime," but new evidence shows pdfium-render is an optional runtime enhancement (dynamic loading), not a mandatory dependency. This revisits the prior decision with updated evidence.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
Option A: Add pdfium-render as optional dual backend — PDFs ≥20 MiB try pdfium first, fall back to pdf-extract if DLL absent. Preserves single-binary property. +9 transitive crates, +7 MB optional DLL. Eliminates DNF for 100+ MB PDFs.

Option B: Accept the limitation — document that PDFs >50 MB are not supported. Zero code change but excludes a class of real documentation (e.g., Azure Cosmos DB 104 MB PDF).

Option C: Fork lopdf to add lazy loading — maximum control, no new runtime deps, but high maintenance burden and uncertain timeline. Upstream shows no indication of lazy-loading support.

Option D: Wait for pdf_oxide — Rust-native, promising, but requires MSRV 1.88+ (current: 1.85). Timeline unknown. Does not solve the problem today.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option A: pdfium-render dual backend. The single-binary concern is addressed by making PDFium an optional runtime enhancement — without the DLL, behavior is identical to current code. The 9-crate compile cost is justified by eliminating a DNF scenario. Options B-D either accept the limitation, require risky upstream work, or defer indefinitely.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. Does the optional DLL violate the "zero runtime dependencies" principle, or is it compatible because the system works without it?
2. Should the DLL be distributed alongside the binary, or should users download it separately?
3. Should we set a formal SLO for large PDF ingestion (e.g., <30s for 100 MB)?
4. Text extraction quality comparison between pdfium and pdf-extract — is the quality good enough for the RAG use case?
<!-- END:open-questions -->
