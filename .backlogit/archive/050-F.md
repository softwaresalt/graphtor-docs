        Read-only, zero-config graphtor context server for agent workspaces (docline generates content -> graphtor builds the db -> agents consume it read-only), with the graphtor dev workspace as the generation+serve exception.

        PRODUCT FRAMING (authoritative intent, per operator):
        graphtor is not primarily a sync engine inside an agent environment. Pipeline: docline authors the standardized Markdown source; graphtor `sync` is a GENERATION-side step that builds a .db from that content (run where the docline content lives); the generated .db is consumed in AGENT workspaces as a READ-ONLY source of context. In a consumer workspace there is no source content, so graphtor should never sync there (sync there is only ever accidental). Modes are separated by ROLE:
          - Generation (authoring/build workspace, has docline output/sources): `sync` content -> .db (write).
          - Consumption (agent workspace, has only .db files): `serve` read-only context (no sync).

        WORKSPACE-MODE EXCEPTION (critical): read-only consumption is the DEFAULT for ALL workspaces EXCEPT the graphtor tool's own development workspace (this repo, e.g. C:\Source\GitHub\graphtor). That one workspace is BOTH a generator AND a server — it must retain the full sync/write path (it builds/tests databases like powerbi.db, postgresql.db from its own sources.yaml). Every OTHER workspace is effectively a read-only server.
        Mode-detection recommendation: derive mode from CONTENT, not a hardcoded path — a workspace is in generation mode only when it has RESOLVABLE ingestion sources with real content (sources.yaml with local sources whose paths exist). Otherwise it is read-only consumption, EVEN IF a stale/empty sources.yaml exists (a consumer workspace must never accidentally re-enable sync). The graphtor dev repo qualifies for generation because it has real sources; consumer workspaces (bare .db files, no real sources) get read-only auto-discovery. Consider an explicit override flag only as a safety escape hatch, but default behaviour must be content-derived and safe (fail read-only).

        DESIGN IMPLICATION: read-only serve is the default posture; the write/sync posture is enabled only by presence of real generation sources (the dev workspace being the primary such case). An agent/consumer workspace's `serve` needs no sources.yaml and no GRAPHTOR_DB_PATH; it exposes whatever .db files live in `.graphtor/`, read-only.

        Current behaviour (verified):
        - `.mcp.json` from install is ALREADY minimal — managed_server_value (src/workspace/mcp_config.rs:273) writes only {command, args:["serve"], transport:"stdio"}, NO env. GRAPHTOR_DB_PATH/GRAPHTOR_SOURCES are operator-added by hand.
        - No env -> `serve` defaults db_path=cwd/.graphtor/graph.db, config=cwd/.graphtor/config/sources.yaml.
        - `serve` discovers dbs via discover_db_files(db_path, source_config) (src/main.rs:2408): iterates config.sources OR a single explicit db_path; does NOT scan `.graphtor/` for dropped .db files.
        - `serve` opens each db read-write (rw_stores) AND read-only (ro_stores) via open_serve_databases (src/main.rs:2344) and spawns background incremental sync (WRITE) when sources.yaml has sources (src/main.rs:2447) — the accidental-resync risk.

        Desired UX:
        - Drop a .db into the root of `.graphtor/` -> `serve` auto-detects and exposes it read-only for query/search/semantic. No sources.yaml, no GRAPHTOR_DB_PATH.
        - Source-backed dbs (a `local` source with an existing path) keep read-write + background sync (generation side); dbs with NO matching real source are served READ-ONLY and NEVER background-synced (no rescan, no v4 prune).

        Design directions to deliberate:
        A) serve auto-discovery of `*.db` in top level of `.graphtor/`; classify has-real-ingestion-source (rw + sync) vs no-source (read-only, no sync). Read-only default; sync only when real sources resolve.
        B) Explicit read-only db entry in sources.yaml (new `type: database` kind, or top-level `databases:` list, or `read_only: true`) for external/aliased dbs.
        C) Combination: auto-discovery zero-config default + explicit entries for named/aliased/external dbs.
        Decide: consumption vs generation is CONTENT-DERIVED (resolvable real sources) by default; optional explicit override flag as escape hatch only.

        Cross-cutting: serve db discovery + role classification; background-sync gating (never sync a no-real-source db, even with a stale sources.yaml); DataStore read-only open (open_sqlite_readonly exists); v4 pre-sync gate still applies to served read-only dbs (refuse/report pre-v4); MCP tool surface + list-sources across multiple auto-discovered dbs (synthesize source metadata from stored doc_sources); status parity; docs (.mcp.json, .graphtor layout, docline->graphtor->agent pipeline + dev-workspace exception, in product-specs/design-docs); security (only .graphtor root, path/containment, skip lock/index/tmp + .graphtor/models + generated artifacts); backward compat (default graph.db + existing sources-driven multi-db serve preserved for the generation/dev workspace).

        Acceptance (high level): in a consumer workspace with a minimal .mcp.json (just `serve`) and .db files in `.graphtor/`, the MCP tools + `status` query them read-only and `serve` never writes/resyncs; in the graphtor dev workspace (real sources), sync still works and it can both generate and serve; a stale/empty sources.yaml in a consumer workspace does NOT enable sync; pre-v4 dbs are gated; docs capture the pipeline + dev-workspace exception. Deliberation first, then phased implementation.

Phase 1 of the consumption-first graphtor theme. Make `serve` auto-discover dropped `*.db` files in the `.graphtor/` root and expose them READ-ONLY, with a CONTENT-DERIVED mode decision (generation/write only when the workspace has resolvable real ingestion sources; otherwise read-only consumption, even with a stale/empty sources.yaml). Gate background sync so a consumer workspace never writes/resyncs a served db, while the graphtor dev workspace (real sources) retains full generate-and-serve. Preserves the v4 pre-sync gate for served read-only dbs.
