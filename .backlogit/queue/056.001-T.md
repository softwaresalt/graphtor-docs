Determine whether the CLI HONORS `cwd` with the temporary, backup-first real-CLI diagnostic-entry probe in the acceptance criteria; do not infer client behavior from the current managed entry, which has no `cwd`, or from a direct child spawn. Goal: identify which pre-serve early-exit / fail-closed path (H0a cwd-relative discovery / H0b lock contention / H0c fail-closed gate) fires, or rule H0 out and point at H1 latency or an H3 client/transport incompatibility — mode A (child alive, initialize never negotiates) or mode B (the real CLI ignores/rejects the requested cwd).

<!-- BEGIN:implementation-notes -->
OS error 232 (ERROR_NO_DATA) is a write to a closed pipe => server exited before handshake. A nonzero early-exit code settles the diagnosis in one run and may make T3 (model lazy-load) and any rmcp bump unnecessary. The cwd-capability probe is operational evidence, not repository implementation: back up the selected MCP config, use an isolated temporary server name and a trusted diagnostic command that records its current directory, invoke it through the actual target CLI, then restore the original config byte-for-byte. See deliberation docs/decisions/2026-08-21-mcp-serve-initialize-os-error-232-deliberation.md. Relevant surfaces: src/main.rs::cmd_serve (~2446-2655), the serve/sync lock entry point is the src/main.rs helper `acquire_database_lock` (~2803-2824), which validates the path and delegates to workspace::lock::DatabaseLock::acquire / handle_existing_lock in src/lock.rs. A genuinely absent default sources.yaml is NOT a fail-closed gate (it falls through to .graphtor/*.db auto-discovery); only a malformed registry or a missing explicit --config exits before serve.
