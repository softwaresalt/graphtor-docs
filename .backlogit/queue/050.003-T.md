Establish an ENGINE/FILESYSTEM-level read-only open for every ReadOnly-classified db (auto-discovered AND explicit workspace-contained entries from P1-T6), plus automated no-write verification, and keep v4 pre-sync gate parity. The read-only open MUST use a backend/open mode that cannot create or mutate the db or its WAL/SHM/journal/lock sidecars (SQLite immutable=1/mode=ro URI or an equivalent SQLITE_OPEN_READONLY connection). Cozo's public SQLite backend exposes NO read-only connection flag and ignores the options string (src/db/store.rs:107-110,384), so the FIRST test-first step confirms engine-level read-only feasibility for the Cozo SQLite backend; if it cannot be PROVEN, the feasibility STOP CONDITION applies (see Implementation Notes): the ReadOnly serve path fails closed AND P1-T4 and shipment 045-S are BLOCKED (Dark Mode halts before Phase 2/minimal install) rather than opening a write-capable handle, claiming INV-1 on the DataStore mutate-guard alone, or silently degrading. Evaluate needs_v4_migration on the read-only store (no write transaction), preserving the refusal message (open_serve_databases:2363), and harden the RO open (disable loadable extensions, disallow ATTACH, constrain to the single file). Sequence AFTER P1-T3; also depends on P1-T6. Test-first.

<!-- BEGIN:acceptance-criteria -->
Three high-level verification scenarios (all substantive checks retained):

(a) Engine/filesystem no-write proof — capture served .db metadata (size, mtime, content hash) and assert NO creation or mutation of the db or its `-wal`/`-shm`/`-journal`/lock sidecars before AND after a full serve+query+search+semantic read cycle (hash and mtime unchanged); an attempted write/mutation against the read-only store is rejected at the ENGINE boundary (not merely the DataStore guard). If engine-level read-only cannot be PROVEN for the Cozo SQLite backend, the feasibility STOP CONDITION applies (see implementation notes) — P1-T4 and shipment 045-S are BLOCKED; never a silent degrade or an INV-1 claim on the mutate-guard alone.

(b) v4 gate parity — a pre-v4 (v3) discovered db is refused with the 'run sync' message (refusal exit); a v4 db is served; the v4 gate (needs_v4_migration) is evaluated on the read-only store with no write transaction.

(c) ATTACH/extension/single-file hardening — a crafted auto-discovered db AND an explicit workspace-contained read-only entry, each attempting ATTACH or a loadable-extension load, are refused/inert, with the RO open constrained to the single file (identical hardening for all ReadOnly entries).

Implementation footprint: < 3 implementation files (src/db/store.rs, src/main.rs) and ONE atomic milestone — an engine-enforced read-only serve open with a passing before/after no-write proof and v4 gate parity.
<!-- END:acceptance-criteria -->
