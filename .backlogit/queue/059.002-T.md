Add safe no-follow handle helpers in src/db/store.rs (test-first): open_no_follow(path)->Result<File,GraphtorError> — Unix: OpenOptions custom_flags(libc::O_NOFOLLOW) (symlink leaf fails ELOOP -> map to existing refusal error); Windows: custom_flags(FILE_FLAG_OPEN_REPARSE_POINT|FILE_FLAG_BACKUP_SEMANTICS), access_mode(FILE_READ_ATTRIBUTES|FILE_WRITE_ATTRIBUTES), share_mode(FILE_SHARE_READ|FILE_SHARE_WRITE|FILE_SHARE_DELETE). Windows open SUCCEEDS on a reparse point, so the helper MUST then inspect MetadataExt::file_attributes() & FILE_ATTRIBUTE_REPARSE_POINT and return the refusal error when set — fail-closed is an explicit code step on Windows, not a byproduct. Attribute-level access (not GENERIC_WRITE) lets an already-read-only file open without ERROR_ACCESS_DENIED. Also capture_perms(&File)->Result via File::metadata(); set_readonly_via_handle(&File,bool)->Result via File::set_permissions (fchmod / SetFileInformationByHandle), preserving exact perms. No unwrap/expect; all errors map to GraphtorError. Doc-comment: identity binding covers final path component only; parent-dir containment stays with caller validate_path (unsafe/MSRV preclude openat/O_PATH).

<!-- BEGIN:acceptance-criteria -->
Test-first, <=3 NEW scenarios written and observed to fail before implementation:
- (a) opens a real regular file and round-trips exact Permissions through the handle.
- (b) refuses a symlinked/junction path: Unix via ELOOP open failure, Windows via explicit FILE_ATTRIBUTE_REPARSE_POINT post-open check, both returning the refusal error.
- (c) set_readonly_via_handle toggles then restores exact original Permissions (Unix mode bits preserved).
- Unix open_no_follow MUST explicitly set .read(true) alongside custom_flags(libc::O_NOFOLLOW): O_NOFOLLOW is only a modifier and an access mode is mandatory (else EINVAL on some libc/kernel combos). Read/attribute access is sufficient for File::metadata() and the handle-bound fchmod restore; write access is NOT requested (least privilege; avoids denying an already-read-only file).
- Windows adopts the BROADER FAIL-CLOSED POLICY: refuse ANY entry carrying FILE_ATTRIBUTE_REPARSE_POINT (not only name-surrogate symlink/junction). Justification: a precise name-surrogate test needs the reparse tag via unsafe DeviceIoControl(FSCTL_GET_REPARSE_POINT) (precluded by #![forbid(unsafe_code)] at MSRV 1.75), and FileType::is_symlink() is path-based (re-introduces TOCTOU). DB paths expect plain files, so the blanket refusal is containment-correct. The Unix/Windows breadth asymmetry is intentional and documented in the doc-comment.
- Helpers compile under #![forbid(unsafe_code)]; pass clippy::pedantic -D warnings; contain no unwrap/expect; symlink/junction open fails closed on both platforms.
<!-- END:acceptance-criteria -->

<!-- BEGIN:implementation-notes -->
All APIs are safe std and MSRV 1.75: OpenOptionsExt::custom_flags (1.10), access_mode/share_mode (1.35), File::set_permissions (1.16, handle-bound), File::metadata. Reuse try_symlink_file for the Unix refusal test and add a Windows junction variant (junction creation does not need the symlink privilege) so the Windows refusal path is not skipped on unprivileged CI. Scope: final component only; O_NOFOLLOW/OPEN_REPARSE_POINT do not guard intermediate components.
