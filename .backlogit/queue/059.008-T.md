U8 BLOCKED. Committed evidence (persisted in the task body, not only in the gitignored .backlogit/logs/ JSONL history):

SOURCE-TRACING EVIDENCE (initial pass): Traced the exact engine-open code path this crate calls (cozo 0.7, storage-sqlite feature; underlying sqlite crate 0.32):
1. cozo-core/src/storage/sqlite.rs new_cozo_sqlite(path) calls sqlite::Connection::open_thread_safe(&path) -- a bare PATH, not a handle/fd/capability object. Reached via cozo::DbInstance::new('sqlite', path_str, options); the 'options' argument is never forwarded to the underlying sqlite3_open_v2 flags (matches the existing src/db/store.rs comment: "Cozo's SQLite backend ignores the options string").
2. DECISIVE: SqliteStorage::transact() -- called on EVERY read and write transaction -- calls sqlite::Connection::open_thread_safe(&self.name) AGAIN whenever its internal connection pool is empty (self.pool.lock().unwrap().pop() == None), where self.name is the ORIGINAL PathBuf captured at DbInstance::new time. cozo does not open the file once at construction; it re-opens by PATH on an ongoing basis for the DataStore's entire lifetime. Even a hypothetical one-time capability-bound open at DbInstance::new could not close this gap.
3. The underlying sqlite crate's Connection::open_with_flags always calls ffi::sqlite3_open_v2(path_to_cstr!(path), ..., vfs: null) -- path-only. It exposes OpenFlags::with_uri() (SQLITE_OPEN_URI), the only plausible same-identity hook (e.g. Linux file:/proc/self/fd/N), but cozo never sets it and gives callers no way to inject it; that trick has no Windows equivalent short of unsafe Win32 OpenFileById/FILE_ID_DESCRIPTOR FFI, which #![forbid(unsafe_code)] rules out absent a vetted safe wrapper crate (none found).
