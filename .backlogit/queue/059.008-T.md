<!-- BEGIN:feasibility-evidence -->
U8 BLOCKED. Committed evidence (Copilot review requested this persist here, not only in the gitignored .backlogit/logs/ JSONL history):

Traced the exact engine-open code path this crate calls (cozo 0.7, storage-sqlite feature; underlying sqlite crate 0.32):
1. cozo-core/src/storage/sqlite.rs new_cozo_sqlite(path) calls sqlite::Connection::open_thread_safe(&path) -- a bare PATH, not a handle/fd/capability object. Reached via cozo::DbInstance::new('sqlite', path_str, options); the 'options' JSON argument is never forwarded to the underlying sqlite3_open_v2 flags (matches the existing src/db/store.rs comment: 'Cozo's SQLite backend ignores the options string').
2. DECISIVE: SqliteStorage::transact() -- called on EVERY read and write transaction -- calls sqlite::Connection::open_thread_safe(&self.name) AGAIN whenever its internal connection pool is empty (self.pool.lock().unwrap().pop() == None), where self.name is the ORIGINAL PathBuf captured at DbInstance::new time. cozo does not open the file once at construction; it re-opens by PATH on an ongoing basis for the DataStore's entire lifetime. Even a hypothetical one-time capability-bound open at DbInstance::new could not close this gap.
3. The underlying sqlite crate's Connection::open_with_flags always calls ffi::sqlite3_open_v2(path_to_cstr!(path), ..., vfs: null) -- path-only. It exposes OpenFlags::with_uri() (SQLITE_OPEN_URI), the only plausible same-identity hook (e.g. Linux file:/proc/self/fd/N), but cozo never sets it and gives callers no way to inject it; that trick has no Windows equivalent short of unsafe Win32 OpenFileById/FILE_ID_DESCRIPTOR FFI, which #![forbid(unsafe_code)] rules out absent a vetted safe wrapper crate (none found).
MISSING SAFE API (acceptance-criteria Scenario 3 naming requirement): cozo::DbInstance / cozo-core::storage::sqlite::SqliteStorage exposes no capability-, handle-, or same-identity-bound engine-open constructor or transaction-reopen hook; only a bare std::path::Path-typed open.
CONCLUSION: no capability- or same-identity-bound SQLite/Cozo engine-open is reachable from safe Rust without forking cozo (out of scope; Constitution Principle VI). Per the plan's own contingency this correctly keeps U1/U2/U6/U9/U3-U5/U10/U11 gated; Constitution Principles III/IV remain NOT-PASSED for feature 059-F. Recommend Stage re-deliberate the engine-boundary approach (Option C per-transact() identity-verified re-open, a narrower leaf-only scope accepting the intermediate-directory residual risk, or an upstream cozo capability-open feature request/fork) before further 059-F work resumes. Full narrative also recorded in docs/memory/2026-08-29/ship-051-s-feasibility-blocked-memory.md and PR #111.
