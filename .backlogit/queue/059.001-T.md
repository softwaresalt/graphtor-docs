In Cargo.toml add libc under [target.'cfg(unix)'.dependencies] (O_NOFOLLOW) and windows-sys under [target.'cfg(windows)'.dependencies], pinned to an already-transitive lock version: windows-sys = { version = "0.61", features = ["Win32_Storage_FileSystem"] }. That feature exposes FILE_FLAG_OPEN_REPARSE_POINT, FILE_FLAG_BACKUP_SEMANTICS, FILE_ATTRIBUTE_REPARSE_POINT, FILE_READ_ATTRIBUTES, FILE_WRITE_ATTRIBUTES, FILE_SHARE_READ|WRITE|DELETE. ALSO add cap-std as a workspace dependency for the U6 (059.006-T) containment-safe beneath-root directory-handle-relative walk, pinned to the newest version that builds under MSRV 1.75; its MSRV-1.75 build AND the required root/intermediate/leaf beneath-root semantics are authoritatively PROVEN in U7 (059.007-T), NOT assumed here — U1 only declares/pins the candidate. cap-std layers on the already-transitive rustix (1.1.4 in Cargo.lock) on Unix and wraps the Windows handle-relative primitives safely, so the supply-chain delta is the cap-std/cap-primitives family only. Add a justification comment (libc/windows-sys already transitive; cap-std is the candidate safe capability API for beneath-root containment, feasibility gated by U7; Constitution Principle VI). Config-first posture, config domain. If U7 records cap-std BLOCKED (no MSRV-1.75-compatible release delivers the needed semantics), do NOT keep cap-std here; the documented fallback (Unix-only safe rustix walk + a separately-specified safe Windows design) is pursued only after its own feasibility evidence, and the decision is recorded in the PR.
