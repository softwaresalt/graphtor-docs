<!-- BEGIN:description -->
SELECTED 2026-08-29 (`selection:selected`). Proven defect: an unhandled pre-`initialize` `server/discover` request is fatal. rmcp 1.5's pre-initialize loop tolerates only `ping`; the client's FIRST request (id 0) is `server/discover`, which breaks the loop, returns `ServerInitializeError::ExpectedInitializeRequest`, propagates through `cmd_serve` (`src/main.rs:2645-2650`), exits 2, and closes the client's pipe. Remedy is a narrow transport adapter between `rmcp::transport::stdio()` and `rmcp::serve_server` that answers exactly that one pre-initialize method, keeps the connection alive, and lets normal `initialize` proceed through unmodified rmcp. Own ONLY transport types and rmcp/stdio wiring; the standing backlog dependency is 056.003-T, and the after-056.015-T ordering is a co-selection-only shipment-assembly edge, not a standing edge. Routed as the sole member of shipment 052-S, which depends on 049-S. Evidence: docs/decisions/2026-08-29-mcp-serve-discover-preinitialize-evidence.md. T4 (056.004-T) alone owns restored-production actual-client acceptance.

<!-- BEGIN:implementation-notes -->
Own only transport types and rmcp/stdio wiring; the seam is a `Transport<RoleServer>` wrapper placed between `rmcp::transport::stdio()` and `rmcp::serve_server` in `cmd_serve`. rmcp cannot be fixed from inside `ServerHandler`: rmcp-1.5.0/src/service/server.rs `serve_server_with_ct_inner` breaks its pre-initialize loop on any non-`ping` request and then fails the `InitializeRequest` destructure at server.rs:201, so the custom request must be answered BEFORE rmcp sees it. That line-201 construction site (payload wrapped as `Request(JsonRpcRequest { .. })`) is the exact shape in the observed stderr; the server.rs:193 site wraps a non-request message instead. rmcp >= 1.4 no longer gates on `notifications/initialized` (the `ExpectedInitializedNotification` variant is `#[deprecated]` and never constructed), which is why the observed message proves ordering: `server/discover` arrives before or instead of `initialize`. `server/discover` is a standardized MCP draft (2026-07-28 era) method, not a vendor probe; the draft stdio Backward-Compatibility section specifies that any error other than a recognized modern error, or no response at all, makes a conforming client fall back to `initialize`, and that the fallback MUST NOT be keyed to one specific error code. Validate by SEPARATE before/after exact-client reacquisitions through the 056.022-T wrapper and 056.023-T observer, not raw-frame replay or persistence. 056.019-T owns client cwd compatibility. Full redacted evidence, remedy constraints, and residual uncertainty: docs/decisions/2026-08-29-mcp-serve-discover-preinitialize-evidence.md.
