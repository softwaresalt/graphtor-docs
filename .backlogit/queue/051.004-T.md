Make the MCP config writer (generate_mcp_config / managed_server_value, src/workspace/mcp_config.rs:84-140) the shared foundation both install paths consume. It provides: (a) a binary-resolution LADDER - reference the pinned absolute .graphtor/bin/graphtor-docs (+ platform ext) when a managed binary exists, otherwise the bare graphtor-docs PATH command (no .exe; Windows resolves via PATHEXT); (b) a managed-entry PROVENANCE MARKER written into the server entry so uninstall (P2-T5b) can identify the graphtor-managed entry; (c) ATOMIC temp-file + rename writes with stable key ordering (Principle IX); and (d) a LOCKED fixed-key collision contract for the `graphtor-docs` key in `.mcp.json`. The current writer does `servers.insert("graphtor-docs", ...)` (src/workspace/mcp_config.rs:131-134), overwriting an unmarked entry using that exact key; replace it with a FOUR-way, provenance-marker-keyed decision on the `graphtor-docs` key (PR #88 review comments 3588876135 / 3588876172, plus original thread E / comment 3585938864): (1) ABSENT -> insert a new managed entry (with the provenance marker) atomically; (2) PRESENT AND carrying the graphtor provenance marker (managed) -> UPDATE it atomically in place (refresh command/args/marker via the resolution ladder); (3) PRESENT, UNMARKED, but EXACTLY matching the legacy generated shape (exact NORMALIZED command equality to `.graphtor/bin/graphtor-docs` OR `.graphtor/bin/graphtor-docs.exe` AND args == ["serve"] AND stdio transport) -> MIGRATE IN PLACE atomically by ADDING the provenance marker and refreshing the managed value: this is the current release's OWN pre-marker entry (R14 backward-compat), NOT a user collision; (4) PRESENT, UNMARKED, and any OTHER shape (user-authored) -> FAIL CLOSED: do NOT overwrite - return a GraphtorError::Config collision error and leave the user's .mcp.json byte-for-byte unchanged. Case (3) uses the SAME exact-equality legacy shape as P2-T5b (051.009-T) removal, never a CONTAINS match. This is the Phase-2 root. Files: src/workspace/mcp_config.rs (+ a shared atomic-write helper if extracted). Depends on Phase 1 (050-F). Test-first.

<!-- BEGIN:acceptance-criteria -->
Three high-level verification scenarios (all substantive checks retained):

(a) writer foundation / happy path — the resolution ladder is unit-tested as a pure function (managed binary present -> pinned `.graphtor/bin/graphtor-docs` + platform ext; no managed binary -> bare `graphtor-docs` PATH command with NO `.exe`); every written managed server entry contains the managed-entry provenance marker; the write is atomic (temp-file + rename) with stable key ordering; and for the `graphtor-docs` key, an ABSENT key -> a new marked managed entry is created and an EXISTING graphtor-managed entry (has the provenance marker) -> UPDATED atomically in place (marker retained), with any other (user) servers preserved.

(b) backward-compat / legacy migration — an UNMARKED `graphtor-docs` entry that EXACTLY matches the legacy generated shape (command == `.graphtor/bin/graphtor-docs` or `.graphtor/bin/graphtor-docs.exe`, args == ["serve"], transport == "stdio", NO marker) -> MIGRATED IN PLACE atomically (provenance marker added, managed value refreshed); this does NOT fail and does NOT count as a user collision (R14 backward-compat for existing installs / reinstall / --with-ingestion); user servers preserved.

(c) fail-closed / preservation — an UNMARKED user-authored `graphtor-docs` key of ANY OTHER shape (e.g. { "command": "my-graphtor", "args": [...] }, or the pinned command but DIFFERENT args/transport) -> installation FAILS CLOSED with a collision error and the user's entry is preserved BYTE-FOR-BYTE (no overwrite); a pre-existing `.mcp.json` with unrelated user servers is preserved (only the managed entry is written/updated/migrated).

<!-- BEGIN:implementation-notes -->
Phase-2 root (thread 7): binary resolution + provenance marker + atomic write must exist BEFORE minimal install (P2-T1) claims a working install. The current writer hardcodes .graphtor/bin/... (mcp_config.rs:86) and always creates it; this task replaces that with the ladder + marker + atomic write + LOCKED four-way collision contract. Legacy-migration case (PR #88 comments 3588876135 / 3588876172): EVERY entry produced by the current pre-marker writer uses the fixed `graphtor-docs` key with the exact pinned command/serve/stdio shape but NO provenance marker (mcp_config.rs:86,95-98,131-134,273-278). A pure three-way rule would misclassify those existing managed installs as user collisions and FAIL reinstall / `--with-ingestion`, contradicting R14; case (3) recognises that exact legacy shape and upgrades it in place by adding the marker, while case (4) still fails closed for every OTHER unmarked entry. Use EXACT normalized command equality (the SAME predicate as P2-T5b / 051.009-T removal) - never CONTAINS - so a user command that merely embeds `.graphtor/bin/graphtor-docs` as a prefix/suffix is treated as a user collision (case 4), not migrated. Fail-closed on a genuine user collision is chosen over silent overwrite because it is enforceable-by-test and consistent with the module's existing non-clobbering posture (it already refuses to clobber invalid-JSON files at mcp_config.rs:110-113 and preserves shared configs on remove). The provenance marker (a dedicated key in the server entry, e.g. an x-graphtor-managed marker) is the single source of truth for 'managed' going forward; the legacy command shape is the ONLY backward-compat recognition path. Both the minimal (P2-T1) and full (P2-T2b) paths consume this writer, guaranteeing marker parity for uninstall (P2-T5b). Bare-PATH fallback carries a documented binary-hijack trade-off; prefer the absolute pinned path when known.
